## Install and use

See `packaging/README.md`. Final build is `dist/linux/atlas-companion-linux-x86_64.tar.gz`, with binary, README, build receipt and checksums. Extract and open `atlas-companion` (preserve executable permission). No admin/Python installation is needed on the tested ABI.

1. Load ATLAS `extension/` in a Chrome/Chromium browser that permits it; obtain the exact extension ID.
2. Open the companion's **Chrome connection** tab, enter that ID, select Chrome/Chromium and explicitly install. Native registration allows only that identity. Installation does not grant any location.
3. In **Authorized locations**, select folders and approve read-only or read/write access. Home, volume and root grants have an additional broad-access warning. Saved grants survive restarts; private native state, installed runtime and protected manifests are excluded.
4. In ATLAS choose **Connect installed companion** once. Subsequent browser/worker activations use remembered enrollment and obtain a fresh session credential automatically without token pasting or repeated folder pickers.
5. Optional **Recovery & diagnostics** offers verified status and explicitly enabled/disabled per-user recovery startup. A working systemd user manager is required; unavailable startup is an error, not a fake success.
6. Revocation/read-write changes and uninstall are in the native application. Uninstall removes unchanged owned registration/launcher/startup files, revokes the enrolled client and preserves user data and prior runtimes. Modified user files are retained. No permanent file deletion is introduced.

CLI source development remains available through `scripts/run_companion.sh`; the source installer snapshots source but still requires Python. The frozen executable supports `install --extension-id ID --consent`, `--state-dir PATH grant ROOT [--write] [--allow-broad]`, `serve`, `doctor`, `--desktop`, and `supervise ...`. Use the same private state directory throughout; XDG settings are respected. No worktree is needed in an already isolated cloud task.

- `atlas_native`: exact registered identity, bounded frames, possession proof before bearer disclosure on the same TCP connection, serialized demand wake, missing/hung service restoration and fixed native-management launch. Revoked or changed identity requires genuine enrollment; recovery grants no scope.
- `supervisor.py`: optional bounded health loop, no bearer transmission or pairing/grants, private single instance, direct-child-only restart after failure, per-user systemd startup with explicit enable/disable/uninstall. Demand wake is independent. No wake timers, sleep inhibition, admin service or work-while-powered-off claims.
- `background.js` / explorer: durable **nonsecret enrollment boolean only**, session-only token, returning UI/startup readiness, one bounded read recovery, preflight wake before mutation submission, no replay after mutation dispatch. Unknown outcomes stay visible until final matching receipt or explicit inspection. Add location opens native management. ### Final Windows implementation details

A Windows empty-port connection can fail without taking Python's immediate ConnectionRefused path. Native wake now performs an exclusive bind availability check after connection failure; this authorizes only starting the fixed helper and never trusting/killing a listener. The Windows server reserves SO_EXCLUSIVEADDRUSE and disables SO_REUSEADDR to prevent competing listeners. A20-second elapsed startup bound permits cold onefile extraction; credentials still require fresh proof on the same connection. Live upgrade/uninstall quiesces optional supervision and only the verified receipt-owned, HMAC-attested helper before bounded executable unlink retries. Missing nested install/state directories are created component-by-component with explicit TokenUser ownership and retained no-reparse ancestors. Login Run uses a receipt/digest-verified short `--recover` command and refuses Windows' command-length limit rather than silently saving unusable startup.
