# Linux Native Messaging installation and wake

This optional development installer requires Linux, Python 3.12 and this stable checkout. It is not a bundled standalone application or Windows installer. Chrome never silently installs it.

1. Load `extension/` unpacked in Chrome or Chromium and copy its exact 32-character extension ID.
2. Explicitly authorize that extension: `python scripts/install_native_host.py --extension-id YOUR_EXTENSION_ID --consent`. For Chromium add `--browser chromium`. The installer registers `org.atlas.companion` for exactly that extension origin. It refuses to overwrite existing installation files.
3. Separately grant each desired narrow folder: `./scripts/run_companion.sh grant /absolute/folder --write`. Omit `--write` for read-only access. No installation or bootstrap operation grants folders. Never grant the companion private state directory or its ancestors.
4. In ATLAS choose **Connect installed companion**. Chrome starts the registered native executable, which authenticates its caller, wakes the fixed local companion if required, and returns a fresh scoped credential to the extension worker. Manual start/pair remains supported.

The default private state directory is `~/.local/share/atlas`; specify the same `--state-dir` to the installer and every companion CLI command when overriding it. Installation prints its three file paths for inspection and explicit removal. Remove the manifest to disable native wake; use `./scripts/run_companion.sh revoke --extension-id ID` to revoke existing authentication. Reinstalling requires explicit removal of the printed installation files first. Revoked clients cannot bootstrap again until explicitly reauthorized.

The host accepts one bounded little-endian JSON message, either `{ "action": "connect" }` or `{ "action": "manage" }`, and no file operation or arbitrary command. The manage action launches only the fixed installed native management application after exact caller/enrollment checks; it never accepts root paths or grants from the browser and does not rotate credentials. The management application asks for separate native scope consent. It checks Chrome's exact caller origin against the installed config and the state binding. Before rotating or transmitting a bearer token, it verifies a fresh nonce HMAC bound to the numeric loopback port using a private state key. Proof and authenticated health use the same persistent TCP connection, preventing a different listener from replacing the proven server between these requests. An unrelated listener receives no bearer token. The host returns `{ok, protocol, port, token}` only after health succeeds; errors contain no secrets.

Each successful native connection rotates the extension's bearer token. The extension worker owns the current session credential; connecting in another browser profile using the same extension identity invalidates the previous credential. Disconnect clears the browser session token; use CLI revoke for durable revocation. This design does not isolate hostile code running with the same OS account and permission to read private application state. Browser requests still use authenticated loopback HTTP; TLS, Windows, reboot/startup recovery and packaged distribution need separate work and proof.

Verification: `PYTHONPATH=src python -m unittest discover -s tests -p test_native_bootstrap.py -v` tests bounded/truncated/duplicate framing, exact-origin explicit installer registration with no grants, actual launcher rejection of an unauthorized caller, real loopback proof/authentication, credential rotation and revocation, actual companion subprocess wake, valid native framed connect, impostor-listener refusal, unsafe installer paths and private-key tampering. A passing Python test does not establish actual Chrome Native Messaging registration/runtime; consult the current handoff for browser evidence.
