# Durable operation history and recovery

The companion already journals accepted mutation intent in private SQLite before filesystem effects. `GET /v1/receipts` now exposes up to 100 newest currently authorized operation summaries, newest first. It scans at most the newest 1,000 durable records to bound work. Historical rows remain in private state for idempotency; the UI history window is not a database retention policy.

Authentication, exact paired extension Origin, numeric loopback Host and no-store headers are identical to every protected route. A record is omitted entirely if ANY source or destination grant has since been revoked; partial cross-grant disclosure is prohibited. Raw requests and extra user-provided fields are never returned. OS error messages are reduced to codes because they can embed absolute paths. Read-only grants may see history but cannot restore.

Statuses are `completed`, `partial`, `failed`, and `pending`. Pending is displayed as `OUTCOME_UNKNOWN`: it means durable intent exists but no final result was committed, either because the operation is still running or the process was interrupted. The client supplies no automatic retry control. Inspect actual filesystem state before issuing another operation. Receipts are observations, not a transaction rollback guarantee.

The `extension/activity.js` module uses the trusted extension worker API broker and its session token. Activity & recovery reopens recorded trash operations after page reload or companion restart. Each Restore creates a new UUID and sends a single opaque trash ID to the existing restore API, targeting ONLY its recorded original grant and parent folder. Existing-file conflicts remain failures; there is no overwrite or permanent delete. Success emits `atlas:refresh`. Previously restored items are disabled when a successful restore receipt is still in the current history window; older or externally restored items safely fail as NOT_FOUND rather than deleting/replacing anything. Missing parent directories require explicit user repair.

The historical receipt is evidence that trash happened, not proof the item still exists. The companion revalidates live grant permissions, directories, symlink boundaries and no-replace publication for every restore. The underlying API can restore to another authorized destination by explicit callers; this recovery UI intentionally restricts itself to original locations.

Verification: `PYTHONPATH=src python -m unittest discover -s tests -p test_recovery_history.py -v` covers actual trash/reopened state/restore byte preservation, partial results, pending outcomes, bounded history, secret-field omission, whole cross-grant revocation filtering, authentication and exact-origin denials over real HTTP. Browser callback behavior needs a Chromium run; Python tests alone do not prove it.
